# Book Pipeline Capability Matrix

Updated: 2026-08-01

This matrix reconciles the launcher Book Pipeline with the local reading workflow and the external Book OCR Conversion boundary. It distinguishes product-core behavior from adapters and manual gates.

Every row is meant to be checkable against the code as it stands. Two conventions keep it that way: a capability that exists in the backend but has no way to reach it from the UI says so in its Status rather than claiming to be automated, and a capability whose behavior differs from the obvious reading of its name says how it actually behaves.

| Capability | Status | Product boundary | Evidence |
| --- | --- | --- | --- |
| Local PDF folder conversion route | Automated, but produces no Markdown or EPUB | Core launcher route, external Book OCR Conversion wrapper execution | `local_pdf_folder` previews and runs `scripts/pdf_to_html_paddleocr.py`, which writes HTML plus its `_state.json` and JSONL sidecars; those, and the output directory, are what artifact scanning normalizes here. No Markdown is written: `full_md` is joined in memory and handed straight to `md_to_html`, so a Paddle-routed local folder has no Markdown artifact for the handoff to pick up — that break is #100. No EPUB comes out of this route either; both builders read `chapters/final/`, which exists only after translation promotion. |
| Zotero attachment discovery and route preview | Automated | Core launcher route, external Zotero worker dry-run | Worker dry-run output is parsed into attachment sources with direct text, PaddleOCR, MinerU, dirty text, and already-converted states. |
| Zotero direct-text attachment execution | Automated | Core launcher route, external Zotero worker execution | `direct_text` runs the worker with `--force-text`; Markdown upload keys are captured on artifacts. |
| Zotero remote PaddleOCR execution | Automated when credentials exist | Core launcher route, external worker/provider execution | `remote_paddleocr` runs with `--force-ocr`; missing credentials block only affected items. |
| Zotero MinerU execution | Automated when credentials exist | Core launcher route, external MinerU wrapper execution | `mineru` runs a fakeable `mineru.py` wrapper contract and normalizes outputs. |
| Zotero collection/filter batch execution | Automated for runnable items | Core launcher orchestration over external per-item workers | Direct-text, PaddleOCR, and MinerU items run independently; dirty, already-converted, and missing-credential items remain per-item blocked/skipped. |
| Collection per-item recovery | Automated | Core launcher retry policy | Parent jobs keep `collectionItems`; retry targets failed items and preserves earlier successful artifacts. |
| Translate-only Markdown/source-text path | Automated | Core local-reading handoff | `markdown_source` stages `.md`, `.markdown`, or `.txt` into a local reading project without OCR. OCR runtime staging paths are rejected by default. |
| Convert-then-translate handoff | Automated after conversion | Core local-reading handoff | Clean Markdown artifacts create the local reading project contract under `books/local/zh-Hans`. |
| Reflection translation strategy | Automated when enabled | Core local-reading handoff plus translation-engine execution | `WindowedReflectionSecondPass` in `packages/translation-engine/src/translation_engine/engine.py` runs the translate/reflect/improve second pass when the manifest sets `secondPassEnabled`. Drafts are written to `qa/reflection/<unit>.draft.md`; the resumable checkpoint under `chapters/translated/.partial/reflection` is keyed on the first pass's id so a changed first pass redoes the reflection rather than blending two passes. Private source text is not logged. |
| Per-job reflection opt-out | Automated | Tauri enqueue intent | `second_pass_enabled` travels from the wizard checkbox (`NewJobWizard.tsx`, fast mode only, default on per `pipeline/model.ts`) through the translation intent into the job and the approval request, and a change to it invalidates a bound approval. Expert mode always enqueues it as `false`. The older `translationStrategy` / `reflectionTranslation` field is a different, superseded line that the frontend never sets; whether to expose or delete it is the open decision in #25, so no draft/reflection/revised handoff artifacts are claimed here. |
| LLM provider selection | Automated | Tauri enqueue intent plus translation-engine registry | Selectable profiles come from the `[[providers]]` registry in `packages/translation-engine/src/translation_engine/providers.toml`, not a hardcoded pair; each entry is a `(profile_id, config_id)` slot, and a brand billed two ways is two slots that must not be mixed. The selected IDs are bound into the approval request. Fake sources always use the built-in fake provider and never spend a real API call. |
| Model credential storage and connection test | Automated | Launcher settings boundary; keys never enter job state | `model_settings.rs` stores one key per `(profile, config)` slot in the macOS Keychain under `com.bibliosmith.launcher.models` and injects it into the registry's `key_env` only when the runner starts the engine. `get_model_catalog` reports `configured` as a boolean; `test_model_connection` exercises a slot without persisting the key into pipeline state. |
| Sample trial translation before commitment | Automated | Core launcher pre-flight over the translation-engine sample CLI | `run_book_pipeline_translation_sample` translates a sample of units through the chosen provider slot so the output can be compared before the full run is approved; `read_book_pipeline_translation_sample` reads the result back. The engine side is `sample.py` / `sample_cli.py`. |
| Custom translation and reflection instructions | Automated | Core launcher job state, engine consumes them per pass | `save_book_pipeline_custom_instructions` persists per-job (or per-child) instructions; `_parse_custom_instructions` in `engine.py` splits them into a translation and a reflection instruction, and each is folded into that pass's idempotency key so changing one invalidates only the affected checkpoints. |
| Zotero title/query search route | Automated | Core launcher route over external Zotero worker discovery | `zotero_filter` accepts `query=` / `q=` / `title=` selectors, resolves them through bibliographic discovery, and enqueues the real child attachments the worker returns rather than the search rows themselves. |
| External adapter artifact contract | Automated adapter boundary | External adapter, core artifact normalization | `external_adapter` runs a configured command with `--input` and `--output-dir`; launcher scans standard artifacts afterward. |
| Artifact contract | Automated | Core launcher | Markdown, HTML, EPUB, metadata, index, output directories, translation projects, translation sources, and reflection phase files are normalized with checksums when applicable. |
| Safe cleanup evidence | Backend only, not reachable from the UI | Core launcher, deletion remains external/manual | `preview_book_pipeline_cleanup` / `approve_book_pipeline_cleanup` require source PDF, local Markdown, output path, and Zotero child attachment evidence before approval, and the launcher records the approval without deleting source files. No component calls the wrappers in `api.ts`, so a user cannot reach this today; the reachability gap and the evidence-binding defects are #21. |
| Versioned parent-child-stage job state | Automated | Core launcher state model | `book_pipeline.rs` persists `book-pipeline-state-v5` with legacy migration, durable per-attachment children, ordered stage records, approval references, derived aggregate status (including `partial`), stage/unit progress, and notification delivery records; atomic tempfile+rename writes use an optimistic revision guard. |
| Federated component state | Decided and enforced at boundaries | Launcher orchestration plus component-owned stores | ADR 0001 keeps launcher JSON, OCR SQLite, per-book projects/checkpoints, and sqlite-vec under separate writers. Job state carries explicit IDs/hashes/contracts/privacy categories and reconciles evidence before reuse; private text is never copied into orchestration state. Resolves the decision requested by #50. |
| Staged-gates translation runner | Automated with explicit approvals | Core local-reading post-handoff runner | `advance_book_pipeline_job` drives deterministic split, prepare, translation, expert QA, promotion, reading build, EPUBCheck, and optional digest stages. `approve_book_pipeline_gate` records either hash-bound decision only after an explicit UI action. The launcher exposes Continue/Approve controls, and its translation action states that source text will be sent. Persisted checkpoints and input hashes support safe reuse/invalidation. |
| Reading output build | Automated after promotion approval | Local reading project workflow | Selected Markdown, semantic HTML, EPUB, bilingual EPUB, validation reports, and optional digest artifacts are built and registered with provenance. Print-specific layout remains a separate workflow. |
| Real-time pipeline progress | Automated | Tauri launcher over public Book Pipeline state | During run/retry/advance the frontend polls `get_book_pipeline_state` and displays persisted stage counts, percent, active stage, and the active unit summary. No React-local progress is treated as truth. Implements the v1 progress choice in #51. |
| Terminal webhook notification | Automated when configured | Launcher terminal outcome boundary | `BOOK_PIPELINE_WEBHOOK_URL` receives a safe event on each terminal outcome. Event IDs and `Idempotency-Key` are deterministic, failures are recorded without changing the job outcome, and source titles/paths/logs/private text/credentials are excluded. Deduplication is **per event identity, not per terminal outcome**: `terminal_event` hashes `updated_at`, `attempts`, and the progress/summary counters into the ID, so a job that re-enters the same terminal status after any state change produces a new ID and is delivered again. Repeat delivery for one `(job, terminal status)` pair is tracked in #28. |
| Scheduled OCR conversion | Disabled by decision | External OCR worker boundary, manual invocation only | There is no OCR timer running for this repository: the user decided to stop the daily job, and it is not to be reinstated as a side effect of reading this table. `packages/ocr/scripts/install_launch_agent.sh` still exists but is not installed; the supported path is running `packages/ocr/scripts/zotero_llm_worker.py` by hand, or going through the launcher's Zotero routes. |
| SRT, DOCX, and TTS | Deferred by decision | Future unified input/output adapters | ADR 0002 defers SRT/DOCX input adapters and TTS reading artifacts to separate follow-up tickets; none are claimed as v1 capabilities. |

## Tracker state is not mirrored here

This file used to carry a hand-written snapshot of GitHub tracker state. That
snapshot is gone. It was taken on 2026-07-17, and the repository rename, the
retirement of the standalone repositories, the open-source rebuild, and the
issue renumbering that followed left it with no line that could still be checked
literally — every issue number in it belonged to a numbering that no longer
exists.

Read tracker state from the tracker. `docs/agents/issue-tracker.md` says which
repository to read and which one is a read-only archive.

The `#NN` references left in the table are cited for a decision or a known gap,
never as a status report, and they come from two different numberings:

- `#25` and `#28` are issues in `semantic-craft/bibliosmith`, this repository.
- `#50` and `#51` predate the open-source rebuild and belong to the archived
  repository. They survive because ADR 0001 and ADR 0002 quote them; read them
  with `gh issue view <N> --repo semantic-craft/bibliosmith-private-archive`.
